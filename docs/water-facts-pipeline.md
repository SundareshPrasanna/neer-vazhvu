# Chennai Water Facts - Update Pipeline

This document describes how each fact card on `/facts` gets its data, how often it refreshes, and what action (if any) is needed to keep it fresh.

## Three data layers

```
┌─────────────────────┐
│  Tier 1 LIVE        │  Queried at request time from Supabase tables.
│  (8 cards)          │  Freshest: hourly via Next.js ISR + cached DB reads.
│                     │  Zero manual action - tables are filled by existing
│                     │  GitHub Actions pipelines.
└─────────────────────┘

┌─────────────────────┐
│  Tier 2 DERIVED     │  Computed at request time from public/data/*.json
│  (6 cards)          │  files. When the underlying JSON is regenerated,
│                     │  the fact auto-updates. File regeneration is manual
│                     │  today (scripts listed below), but trivial to run
│                     │  on a GitHub Actions schedule.
└─────────────────────┘

┌─────────────────────┐
│  Tiers 3 & 4 STATIC │  Hardcoded strings in src/lib/facts/static-facts.ts.
│  (9 cards)          │  Historical milestones and structural facts.
│                     │  Only updated by code change - typically on a
│                     │  multi-year cadence.
└─────────────────────┘
```

## Recommended automation additions

The per-card table above shows Tier 2 already "auto-updates" in that any JSON file refresh propagates to the facts page without code changes. But those JSON files are currently regenerated manually. To close the loop:

1. **Add `fetch-wris-groundwater.ts` to a GitHub Actions quarterly cron.** CGWB publishes the GWR assessment once a year; running the script quarterly catches any off-cycle releases within ~3 months.

2. **Add a monthly check for OpenCity publication dates.** When the Nov-of-each-year OpenCity release lands, the `LAST_PUBLICATION` constant in `derived-facts.ts` needs updating. A monthly workflow that hits `data.opencity.in/dataset/chennai-ward-wise-groundwater-levels` and opens a PR when the published_date changes would remove the last manual step.

3. **CPCB annual report watcher** is harder because CPCB distributes only PDFs. Consider setting up a cron that fetches the `https://cpcb.nic.in/nwmp-data-2/` directory listing and opens an issue when new file names appear, so a human reviewer can extract into `river-quality.json`.

## Editing a fact

If the underlying data has not changed but you want to rewrite the copy or fix a typo:

- **Tier 1 cards**: Edit the corresponding builder in `src/lib/facts/live-facts.ts`. Hot reloads; no code deploy needed for the next hourly rebuild.
- **Tier 2 cards**: Edit the builder in `src/lib/facts/derived-facts.ts`.
- **Tiers 3 and 4 cards**: Edit the object in `src/lib/facts/static-facts.ts`.

Every edit should preserve the canonical `Fact` shape defined in `src/types/facts.ts`: `data_date`, `published_date`, `retrieved_at`, `source_url`, `source_label`, `method_id`, `quote_text`, and `claim_status` are required so that the copy-quote button, JSON-LD structured data, and PDF press kit all stay consistent.

## Rendering pipeline

```
Request to /facts or /api/facts
        │
        ▼
┌─────────────────────────────────┐
│ Promise.all([                   │
│   buildLiveFacts(),             │  ── Supabase queries
│   buildDerivedFacts(),          │  ── fs.readFile on public/data/*.json
│ ])                              │
└─────────────────────────────────┘
        │
        ▼
  merge with STATIC_FACTS
        │
        ▼
┌─────────────────────────────────┐
│ ISR cache (revalidate: 3600)    │  Same rendered HTML served for up to
│ or JSON response (max-age 3600) │  1 hour, then regenerated on next hit.
└─────────────────────────────────┘
```

Live and derived facts are computed in parallel with `Promise.allSettled`, so a single failing builder (bad DB connection, missing data file) doesn't break the page - the other cards still render.
